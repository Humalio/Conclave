# Threat model

Protect credentials, private vault bytes and metadata, local PC files, workflow state, and audit integrity. Assume an agent may be prompt-injected or deliberately misuse its grants; peers, synced files, uploaded paths, and curator output are untrusted. The admin, host, and bridge machine accounts are privileged. An attacker who controls one of those accounts can defeat some of the corresponding protections.

| Boundary and failure | Controls and remaining exposure |
|---|---|
| Client → MCP: stolen key, forged identity, unauthenticated request, browser-origin abuse | Authenticate the app and bind the login token to that app; recheck key state. Use short session lifetimes and revoke or rotate suspect keys. A session key bound to a PC logs in only through an app key on that PC, so a session key leaked without its PC's app key fails elsewhere, alerts (`bound_key_elsewhere`) and is audited; binding does not stop a holder of that PC's app key, and free keys (the default for keys created by hand) work from any permitted PC. Origin checks do not replace transport security. A shell-capable agent may read the client's app config. |
| MCP → domain: overbroad grants, confused deputy, stale permission, enumeration | Deny by default; deny overrides implicit and temporary allows. Intersect app cap with session rules and check current membership/role/pauses. Use indistinguishable denials where existence is sensitive. Filter before exposing results, including counts, snippets and provenance. |
| Agent ↔ agent: prompt injection, relay of private data | Trust labels, bilateral direct-message policy, room permissions, separate review, and operator audit. A legitimately authorized reader can still disclose what it learns. Limit both read and outbound communication grants. |
| Connector → hub: a PC reports a message as shown to a session | The report is a position only (no message text), accepted only for an agent whose key is bound to that PC. The console labels it "reported by the PC" and never treats it as Read: only the agent's own acknowledgement is. A PC that lies can mark a message shown, not read, and cannot change what the agent may do. |
| **Message text or an instruction reaches the agent through the reminder line or the folder hook.** A message, a sender label or a directive title written to carry instructions tries to ride in the one line that is added to the agent's context. | The line is built on the PC from the hub's counts in fixed words and carries no text, title or id. A sender shows only as "the operator", or by a plain label (letters, digits, spaces and a few separators, at most 40 characters and five words) and otherwise as "an agent"; tests cover a label that carries instructions. The hook adds context only: it prints no `decision`, `continue` or `stopReason`, so it cannot block a prompt, and no Stop hook is registered (printed context at Stop makes Claude Code continue the turn; a build test fails if any is registered). It does nothing on a timeout, a hub error or a folder that is not registered, and it is written only into an agent folder's own project settings, one entry at a time, never the user's own settings. |
| Vault and graph: traversal, symlinks, accidental overwrite, derived-data leaks | Confinement and hidden path rules; revision checks, history, and conflicts; current source filtering for graph outputs; quote validation and independent review. Local filesystem races and malicious L2 content remain possible. |
| Hub ↔ bridge: unauthorized local access, hostile framed paths, interrupted transfer | PC-scoped credential and job assignment; approved folder checks on both sides and checks during extraction; bounded buffers, offsets, size/hash and completion verification. Folder approval is a real local access boundary; avoid broad roots. |
| Admin browser → API: credential theft, CSRF, sensitive exports | Local passwords hashed with scrypt, optional enrolled TOTP, cookie sessions and CSRF checks. Protect the console and exports as privileged data. Lockdown applies to agent activity; the operator retains recovery access. Admins can do everything the console does; a stolen admin session is a full compromise. An admin can reset another admin's password (`POST /api/users/:id/reset-password`, audited as `user.password_reset`) and, if that admin has not enrolled 2FA, sign in as them with the new password; mitigation: every admin enrols 2FA. |
| Member task board: a member reading another project's tasks, an external partner reading internal task text, agent ids reaching members, a write through the board | Off by default per project (`projects.member_board`, admin-only switch, audited). When on, only members with a grant on the project read it; external users never do. Every refusal (switch off, no grant, unknown project, external user) is the same `403 board_denied`, and a task of another project or off the board reads as `404`. Cards carry agent labels, never agent, key or console user ids; backlog, discarded and cancelled tasks are left out. The routes are read only; task acts keep their own scopes. Tested in the [member board suite](../server/test/member-board.test.ts). Remaining: a member can disclose task text they legitimately read. |
| **Task attachments: who reads them, and what an attached file can do to an agent.** A screenshot of the operator console reaches someone not cleared for it; an attached share widens who reads someone's files; a share another team sent the caller is copied into a task its whole team reads; text in an image steers an agent. | **Controls:** Attachments live in hub-made shares bound to one task; only the operator and the agents of the task's team who may read that task (its coordinator, creator, assignee or reviewer) can open them, checked again on every request, so a former assignee is refused at once; nobody reads them once the task is cancelled or discarded. Project members see a count, never a file; external members see nothing. A share given at submission or with `attachments_from` is copied (content-addressed blobs), never rebound, so its own readers don't change, and **only a share the caller made can be copied**, so a share someone sent the caller cannot be widened to a task's team. Share tools other than reads refuse a task-bound share, and `share_list` leaves them out. Every file is L2 data; `share_read` returns images with the L2 label. Key and environment file names are refused. Limits per file, task and team; lockdown refuses new attachments; a cancelled or discarded task's attachments are deleted 30 days after it closes. **Remaining:** An agent of the team, or the operator, sees whatever a screenshot shows, including other teams or a key page, if the author didn't crop it. Text inside an image is read by a model as content, and only the L2 rule stands between it and an instruction. A static mockup can still mislead by what it draws. **The console's byte route** (`GET /api/tasks/:id/attachments/:role/file`, operator only) decides the type from the bytes: four image types inline, HTML only with `as=mockup`, everything else (SVG, renamed files, HTML without `as=mockup`) as a download. Every answer carries `nosniff`, `Cross-Origin-Resource-Policy: same-origin`, a private cache and a CSP `sandbox` (an opaque origin even when the URL is opened at top level); a mockup's CSP allows inline styles and `data:` images and fonts only, and the console frames it with a sandboxed iframe that has no `allow-scripts`. A removed set and a wrong path or version answer the same `not_found`. A mockup can still mislead by what it draws. |
| Member browser → API: cross-project leak through derived data (graph entities and relations, search hits and snippets, Work in motion, topology edges, counts and badges, "N more", pagination cursors, export files, 404 against 403 on ids, `/api/me`), a stale grant (a revoked grant or an expired user still served), an external partner reaching restricted folders | Every route declares one scope in a registry and an undeclared route is admin-only (fail closed). Lists filter before paging, limits and counts; an out-of-grant id answers exactly like an unknown id. Grants are rebuilt and rechecked on every call, so a revoked grant or an expired user stops at the next call. External users need 2FA, never get restricted folders and have no export by default. There is no setup link or registration page: the hub generates each new or reset password (about 116 bits), stores only its hash and returns it once to the admin who created or reset the user, so that admin sees it once and could keep it; the user replaces it with their own from Account (`POST /api/me/password`, which ends their other sessions), and a reset ends all of the user's sessions. The leak test walks every registered route with another project's ids ([multi-user](multi-user.md) §5). Remaining: a member can disclose what they legitimately read; timing differences are not covered. |
| Decider acts: a decider approving beyond what the team allows, escalating to Blueprint items outside their team's part, or acting after losing the role | A decider acts only on items routed to their team, and only while they are an active decider (granted the project, set up, enrolled in 2FA when required, not expired). Access requests are approved only inside the team's ceiling, which never overrides a deny and never covers a restricted folder, and is rechecked at decision time. Blueprint writes are limited to status moves on existing items of one team they decide for; project-level items, other teams' parts, text edits and removals stay with the admin. Each routed act is audited with `via` and the team. Remaining: a decider's answer binds the team as the operator's answer would, and an admin can override it. |
| Inputs/outputs and logs: accidental credential exposure | Scan agent input and withhold detected outbound secrets; redact audit details, alert, and suspend the offending session key on inbound detection. Encodings, binary content, and external clients' logs or chat storage remain outside complete coverage. |
| Key prompts (a new, rotated or reissued session key): a leaked prompt, a lost one | A key for a known PC travels by a single-use pickup code that only an app key of that PC redeems, within 7 days, and the script writes the key into `keys.env`, outside any repository ([key prompts](onboarding.md#key-prompts-a-new-rotated-or-reissued-session-key)). **Accepted exception:** a free key with no PC is shown raw, once, in the console, with a warning not to paste it into a chat; bind the key to a PC to avoid it. The one-time view asks before it closes uncopied and offers no download. A lost prompt is replaced by **Make a new prompt**, which voids the old key and code (audited as a rotation). Changing the key's PC binding voids an open code, a bound key's code works only while it is bound to that PC, and a lockdown of all writes, the PC or the agent refuses the pickup. |
| **The Codex wake collects a rotated key** ([collect on a PC](onboarding.md#collect-on-a-pc-the-codex-wake-picks-up-a-routine-rotation)). Someone on the PC, on the network, or holding a copied keys file or another agent's app key tries to take a key armed for collection; a second copy of the wake collects first; or a collection that never reached the keys file leaves a live key nobody holds. | **Controls:** Opt-in only from a user-only file on the PC (`collect_keys`), never from the hub. The operator's click (admin, CSRF, audited) arms the collection, **only for a routine rotation** (`reason: routine`) of a key that has logged in: after a suspected leak the hub refuses Collect, and the sheet sends the operator to rotate the app key and use a key prompt. No code exists and no secret is stored; the key is created at pickup. The collection is bound to the key's PC, to the one app key the old key last logged in through, and to the instance id of the wake that polled for it. Collect is refused when that app key is shared: when the hub's own login records show it served another agent's session key in the last 30 days, or when the wake polled for more than one variable with it. A pickup from another PC, app key or instance answers "not found", counted and rate-limited as a wrong pickup code. **A second collector** (a second instance id for the variable, or one instance from two addresses) raises `key.collect_conflict` and voids the collection. A login with the collected key through **any app key other than the bound one, on the same PC or another**, is refused (from another PC as `bound_key_elsewhere`), voids the new secret, raises `key.collect_conflict` and shows Failed, never Signed in: the hub compares the login's app key with the collection's, not only its PC. The poll returns no secret. The pickup is single use, HTTPS only with the pinned hub CA, refused under lockdown, and voided by a binding change, Cancel or expiry (24 h). The wake writes only that entry's keys file (temp file and rename, mode 600), never puts the key in a Codex environment, argument or log, and must confirm within 10 minutes or the hub voids the secret. **Remaining:** Collection is offered only for a routine rotation of a key that has logged in; after a suspected leak the operator rotates the app key and uses a key prompt. Whoever holds that agent's keys file, and so its app key, can collect a routine rotation while one is armed (at most 24 h). A second collector is detected by its instance id and voids the collection, and a login with the new key from another app key is not shown as Signed in. Where agents share one app key without the hub seeing it (no login or poll for the other agent in 30 days), each can collect for the others. The agent is down between rotation and collection, as today. |
| **Installer and updates:** the hub, or someone in the middle, serves a tampered connector; a downgrade to a weak version; a lost signing key. | The installer and every update are signed by a release key that is not on the hub, and checked against a key the connector carries, independently of the hub, for signer, version and platform. Downgrades the hub asks for are refused. Rollback goes only to the previous verified build on the PC. Key rollover is signed by the old key. The maintainer approves each version; the PC user can turn updates off. A private git, when the user accepts it, is a pinned version checked against the hash in the connector's signed release. **Remaining:** whoever holds the release key can ship code to every PC that updates. Flaws in that git version until the next connector release. |
| **Pairing:** a code read from a chat or a log; a second hub with the same CA; a CA swapped in later. | The code appears only in the console and on the local pairing screen, never in a prompt, chat, argument or log. It lasts 30 minutes and is bound to the hub's identity, origin and CA pin. A changed CA or origin needs the PC user's local confirmation. A web pairing screen listens on loopback only, with a one-time token and an origin check. **Remaining:** someone at the user's screen during those 30 minutes. |
| Onboarding: a leaked prompt, stolen PC key, leaked session key, replayed pickup, tampered setup script, over-broad request, request text aimed at the operator | **With the connector, the prompt holds no code:** the pairing code goes only into the connector's local pairing screen and expires after 30 minutes (row above). For a PC without the connector, for one more release: the prompt holds a single-use enrolment code, never a key; the model and the transcript see that code until it is used, and the script reads it from a file or stdin, never the command line; reuse is refused and alerts; an unused Add PC code has no timer, so the operator revokes unused codes; a code a checkout issues expires after 30 minutes. Keys have no expiry, so revocation is the control: Re-enrol PC revokes the PC's app key, onboarded session keys and any unused code at once. The app key's capability allows only filing, status and pickup, and is withdrawn when no longer needed; one pending request per key; one operator approval with access computed from structured fields and request text rendered inert as L2; keys created at pickup, unconfirmed sets revoked on retry, pickup after confirmation refused with an alert, pickup only by the filing app key; setup files checked by hash and every setup call over HTTPS pinned to the hub CA. Every session key has a PC binding switch (onboarded keys bound by default); it stops a session key leaked without its PC key, but not a thief holding the PC key, which satisfies it, with the session keys in the same `keys.env`. Setup always uses HTTPS pinned to the hub CA; for MCP the user chooses between trusting the CA and plain HTTP with a warning, and on plain HTTP keys cross the LAN in clear at login. See [onboarding](onboarding.md#threat-model). |
| Blueprint: agent-written items read by other teams and the operator | Trust per item: bp_read labels each item from its creator and its last writer (the lower wins): the operator, the hub and the docs import are L0, an agent of the reader's team L1, any other agent L2; index lines name who last changed the item and the answer carries the lowest label. The rights matrix and proposals keep another team's agent out of your part, and agent text in reasons and notices stays out of hub-written notices. An operator's status move does not raise an agent's text to L0 (the lower label wins), and a proposal the operator applies keeps its proposer as the writer. Remaining: a label is advice to the reader, not a filter; an agent that follows L2 text it was told to treat as data is not stopped by the hub. A re-plan (start over) widens a coordinator's rights only to the items the operator marked in its own part, never to agreeing requirements; its reset and applied statuses keep each item's writer, so a reset never raises an agent's text to L0; the snapshot is admin-only, and cancel restores it. |
| Checkout: a handout as injection on the target, a forged checkpoint, a stale or stolen restore login, leftovers on the source | Handout fields are typed (refs with no leading `-`, 40-hex heads, folder names and URL hosts that start with a letter or digit, provider enums, 1500-character notes); a repo URL must name a host on the operator's allowlist (exact host, case-insensitive, in https, ssh and scp-like forms, no wildcards, never a leading `-`), checked at `checkout_handout`, again at render and at pickup, and audited when refused; the hub writes the checkpoint from the report, never from the handout. Notes come back once, to the resuming agent only, labelled L2, and never reach the restore prompt. The handout hash is checked at pickup and at resume; it is consumed once, and its body is cleared once its vault copy is written (at most 7 days later). Resume needs a login of the successor key made after confirm (or after render, when keys are kept). The leftover check is self-reported: every kind must be reported, exceptions need a reason and the operator's approval of the exact report seen (its hash), and refusals carry a note; their text is L2, one line and labelled. The config scan is self-reported too: the target's client lists what it found, and the hub holds every key until each folder has a scan and none waits for the operator. A modified client can hide findings, but it harms only its own PC. A restored checkout skips the scan check at pickup. A handout built by the hub carries only a complete checkpoint; otherwise the work is listed as unmerged on the source and kept off the push list. Remaining: a same-user move that keeps keys cannot tell a source session that logs in again after render from the target; the hub cannot see the disk, so a leftover or scan report can be false; the restore proves the recorded commits exist, not that the source is clean. |
| Vault copy (`99 Conclave/`): agent text and keys copied into the vault, an agent rewriting the hub's record, mirror pages crowding the graph or backlinks | Every page passes one filter: https user parts dropped; Conclave keys, third-party tokens and private key blocks redacted; body fields named like a secret left out; then the leak guard checks each section as written, and an issued key (even split across lines) withholds it and raises `key_in_result`. No page holds a restore prompt or pickup id. The policy engine refuses every agent write under the folder whatever the rules say; reads need a rule that names the folder; `file_search`, backlinks and the graph skip it; console members see it only when granted by name. Remaining: the filter is pattern-based, so a secret in an unknown shape reaches the page as the agent wrote it (it was already in the hub as L2 text). |
| **Delegating one agent to a collaborator's PC.** The collaborator, or someone who intercepts the prompt, uses the agent beyond what the collaborator may do, enrols a PC that isn't theirs, or keeps the key after Take back. | Only the admin delegates. The prompt is shown only in the delegate's own console, behind sign-in and 2FA. A new PC needs the delegate's "this is my PC" and then the operator's approval before any secret is released, with a 30-minute single-use code. The successor key is bound to that PC, and old tokens are suspended at confirm. While delegated, the delegate's grant is a ceiling on the agent, whatever the owner setting. Take back revokes the key and its tokens at once, lifts the ceiling, and offers to retire a PC enrolled for the delegation. Contributor mode, so the delegate changes only what they created; everything else is a proposal labelled with their name. **Remaining:** the delegate controls the PC and so holds the agent's key and that PC's app key. Until Take back, they can use the agent from any tool on that PC, within their own grant. Work on their PC is not recovered by Take back. |
| Owner enforcement: an agent acting past its owner's grant, a collaborator's agent steering the admin's agent through a task, a revoked owner whose agent keeps working, work done outside the hub | While the setting is on, each owner's delegated grant is a ceiling on every decision (reads, writes, rooms, peers, shares, the graph, the Blueprint). It is built again on every call and checked again when a write commits, so a narrowed grant, a disabled owner or a lost membership applies to the next operation. Unmapped operations are refused. Work handed over by another owner's agent is labelled with that owner and capped at that owner's grant while the recipient acts on it. Remaining: the hub cannot see what an agent does in a repository or on its PC with access it has there (git credentials, local files, other tools). Handed-over text can still persuade an agent to act there. Notices are not filtered by owner. |
| Reviews woken by the bridge ([Codex wake](connector.md#codex-wake)): a submission steering the woken reviewer, a key reaching Codex, a hub message starting a turn, runaway or duplicate turns | Opt-in only from a file on the PC that only its user writes; the hub cannot set it. Only a `review_requested` item with a task id matching `^task_[a-z0-9]{1,40}$` starts a turn; the prompt is fixed text with that id. Codex runs read-only, never asking, from an absolute `.exe` with no shell, with an allowlisted environment that holds no Conclave key. One turn at a time, 6 an hour, 30 minutes each, then the process tree is killed. The wake used to read none of Codex's output; it now reads stderr only to match one fixed text ("already has an active writer", on a tail kept shorter than that text), so it can tell the operator to use a dedicated review session. Nothing read is logged, stored or forwarded, stdout is discarded, and after the turn exits the wake waits at most 250 ms for stderr, so a child that inherited it cannot hang the wake. The item is confirmed only once the verdict is on the hub, and a submission with a verdict never starts another turn. Review text with a Conclave key is refused, alerted and the key suspended; other secrets are redacted with the vault copy filter and alerted (`review_redacted`). A woken reviewer can still be misled in what it writes; its verdict is one input the coordinator weighs. Remaining: the turn runs as the PC user and a read-only sandbox still reads files, including the keys file named on its command line, so a hostile submission could steer it to put a key into the review, which the submitter reads. The leak guard and the redaction are the only backstop and match known shapes only, so an encoded or split key gets through; give each woken reviewer its own keys file and app key so a leak costs one rotation. |
| **Hub → PC actions** (check, restore, update, disconnect): a stolen admin session, a forged or replayed order. | A fixed list, admin-only, CSRF, audited. Orders arrive only on the pinned poll, bound to the installation and a one-time id, with typed data; a path or command makes the order invalid. Restore goes only to a destination the PC user approved, with checkout's validation. **Remaining:** an admin can do everything the console does, now also these actions on every connected installation. |
| **Disconnect:** files outside Conclave deleted, another hub's setup broken, cleanup lost halfway, a user's edits lost. | Scoped to the issuing hub; the connector goes only when no hub remains and the user chose that. Only connector-owned entries of fixed kinds, checked against root and filesystem identity (symlinks, junctions, reparse points) at the moment of change. Shared config is undone only while it holds the installed value. Edited files are kept and listed. A journal resumes cleanup. A narrow receipt credential is retired after the receipt. Only processes the connector started are ended. The user can turn remote disk cleanup off. **Remaining:** an installation that never polls again keeps its files; its keys are already dead. |
| **Folder trust and restore:** the connector trusting a folder the user withdrew, or one that changed under it. | Trust is put back only for a registered, unchanged folder whose entry disappeared. A withdrawal or a changed folder gets **Repair connection**, which asks. Restore asks before trusting a changed folder and keeps the config scan. The hub cannot add a folder. **Remaining:** a change made on the PC by the user's own tools between two checks. |
| **Usage stats:** transcript text leaving the PC; personal chats counted; liveness guessed from files. | Opt-in on the PC. Only aggregate numbers, from registered worker sessions, with the recorded folder checked. Structured client events where they exist. Nothing read is logged. Liveness only from the connector's own process state, otherwise **Unknown**. Costs at API list prices, admins only. **Remaining:** the reader runs as the user and could read the files; the control is its code and the release test. |
| Service availability: resource exhaustion or crash | Bounded requests and polls, persisted rate counters, transfer caps, retention, and write-intent recovery. Monitor storage and keep independent backups. A single process remains a single failure domain. |

When changing a boundary, test app/token mismatch, deny precedence, revocation after queueing, path escape, and indirect disclosure where relevant. For asynchronous flows, check authorization at delivery and commit, not just at enqueue. Reference tests: [integration](../server/test/integration.test.ts), [graph security](../server/test/graph-security-regressions.test.ts), [bridge lockdown](../server/test/lockdown_bridge.test.ts), and [bridge path checks](../bridge/test/path.test.mjs).
