# Vault and knowledge graph

The operator works with the knowledge graph in **Vault → Knowledge**. See [In the console](#in-the-console).

The vault is a configured Obsidian-compatible directory. Paths are of the form `/vault/Projects/plan.md`, with a configurable alias. The path resolver excludes hidden application and sync folders, temporary write files, reserved `shares`, and unsafe path forms. Never accept a host path from an MCP vault caller. Permission to traverse a folder may reflect reachable descendants; it does not grant access to every item below it.

Use `file_list` to browse, `file_stat` for metadata and readable backlinks, `file_read` for current text, and `file_search` for case-insensitive text search. Search is a bounded scan over files the session can read and search. Paginate text with byte offsets; use history/diff tools for revision inspection and authorized downloads for binary content. Writes, external changes and recovery follow the [filesystem consistency design](filesystem-consistency.md). The [dashboard](dashboard-ux.md#vault-workspace) exposes these operations from a folder or file context.

## Deriving knowledge

The graph is an aid to find evidence and review the effects of a change. The hub runs no model. It splits notes into sections with heading anchors and normalized hashes. Vault changes update section state and signals such as links, embeds, frontmatter dependencies, near-duplicates and read-before-write provenance. Candidate impact is a ranking with reasons, not a verdict; weak signals such as tags or co-changes do not trigger impact checks alone.

Crash recovery reconciles the graph with the committed revision of every file it touches. A write the crash left half-done or had just finished is indexed as committed; a deleted file leaves the graph (its sections, signals and queued jobs); a renamed file is reindexed under its new path, its own links are resolved again, and links to it are resolved again in both directions (a link by the old name no longer points at it, one by the new name now does). A write's intent stays recorded until the graph has seen the change, so a crash between the metadata and the graph update is finished on the next start. The same holds when the graph fails to take a change while the hub runs: the intent is kept and the change is given to the graph again at the next scan, and at the next start if the hub stops first. Recovery of a rename looks for the renamed file at its new path first, and at its old path only while that still holds the renamed content, so a new file made at the old path since is never taken for the renamed one. Recovery is idempotent: running it again changes nothing and queues no second job. Renames by the hub and renames the scan infers from a matching disappearance and appearance update the graph the same way; a file renamed out of Markdown or into `99 Conclave/` leaves it. Curator sessions take leased jobs through `work_next`. The hub debounces edits, can batch small indexing jobs, enforces input budgets, and checks current access on delivery and redelivery. Initial scan is not a semantic indexing pass; coverage depends on eligible curators, reads, and edits. Without curators, deterministic links and impact signals remain useful, but semantic coverage is partial.

| Job | Result |
|---|---|
| `index_note` | Entities, claims and relations from changed sections. Claims need a valid anchor and exact supporting quote. The hub rejects stale source sections and invalid evidence. |
| `impact_check` | Before/after and readable candidates. Give every candidate a supported verdict: ok, stale, or contradicts. Editors can opt in for a short first offer on their own writes. |
| `verify_sample` | A different session checks extracted claims. Disagreement can dispute a claim and affect future job routing. |
| `entity_merge` | Resolve aliases without merging look-alikes. Larger merges go to independent review. |
| `refresh_summary`, `summarize_community` | Produce summaries with complete source provenance; withhold a stored summary unless all sources remain readable. |

Claim conflicts and stale evidence can raise flags and create reviewable tasks. Curators report the problem; fixing a note uses ordinary vault tools and permissions. Resolution must show the relevant change or a reviewer dismissal. Generated notices and tasks carry references; use `graph_stale` to inspect details under current source permissions.

Use `graph_related` and `graph_impact` to choose where to look; use `graph_context`, `graph_query` or `graph_summary` for a bounded evidence pack. Cite source path, section, and revision, and reread the cited section before acting on important claims. Filter provenance, flags, summaries, counts, and task detail as carefully as raw bytes: even a name can reveal a private note. See [graph implementation](../server/src/graph/) and [MCP schemas](../server/src/mcp/graphTools.ts).

## Scheduling and provenance

The write observer compares section hashes and marks affected claims `source_changed`. Frontmatter `depends_on` and `source` are explicit signals. External edits have no known writer or read set. Personalized PageRank ranks impact candidates from the changed sections.

| Control | Current behavior |
|---|---|
| Queue | Debounce edits for two minutes. Allow one live indexing lease per note. Rebuild redelivered batches from jobs the caller still owns and can read. |
| Lease | Ten minutes, renewed by authenticated activity while live. Expired owners can receive `lease_expired`. Three failed attempts park a job. |
| Batch | Up to 6,000 estimated input tokens. Submit each member separately with its own job ID. Completed jobs need no `work_ack`. |
| Budget | Default 200,000 estimated tokens per vault per day and 60,000 per session per hour. Ordinary priorities can use 80% of a cap. Delivered input remains charged after expiry. |
| Routing | Match light and strong tiers to configured model-label patterns. Raise priority for selected folders and lower indexing priority during bursts. Model labels never grant access. |
| Verification | Sample about 10% of accepted indexing results and results containing claims below 0.6 confidence. A different session verifies them. Sustained disagreement can restrict job routing. |

Claims track source-stated validity separately from when the hub recorded or invalidated them. `graph_query.as_of` selects by hub record time. Community summaries depend on every source used, including sources behind entity names. Operator health includes coverage by folder, flags, queued and parked jobs, spend and verification. Agent-facing health is source-scoped. See [graph defaults](../server/src/graph/graph.ts) and the [admin API](../server/src/admin/graphApi.ts).

## The hub's folder: 99 Conclave

The hub writes read-only Markdown copies of its own records into the vault folder `99 Conclave/`, so the operator can read them in Obsidian after the records themselves are gone. The copies come from the [mirror](../server/src/mirror/mirror.ts); its paths are kept in `mirror_files`, which no reset part wipes.

```
99 Conclave/
  README.md                              index: projects and teams, with teams no longer in the hub
  <Project name>/                        "<KEY> <Project name>" only when two live projects clean to the same name; "No project" for a team without one
    <Team name>/                         " (2)" when a team of a reset hub had the name; a rename keeps the folder
      Team.md                            goal, settings, members, open tasks, links to the records
      Sessions/<label>.md                one per member; " (agent-…)" when two labels clean to the same name
      Checkouts/<YYYY-MM-DD> <cko_…>/
        README.md                        status, dates, source and target, push list, handouts, outcome
        <label>.md                       one per handout: the checkpoint report and the body's local facts
      Reviews/<YYYY-MM>.md               every review verdict of the month, with its comments
      Decisions.md                       the team's answered and declined questions
```

- **When.** Every trigger runs after the transaction that caused it has committed and reads the records back, so a sweep that rolls back writes nothing. A checkout's pages follow each of its steps (start, handout write, ready, render, restoring, restored, the end); a review verdict rewrites that month's page; an answered, declined or overturned question rewrites `Decisions.md`; `Team.md` and the session pages are written once per team, 5 minutes after a change. At start-up and every hour a sweep writes any page that is missing or out of date; with vault scanning off (`VAULT_SCAN_SECONDS=0`) the hourly run is the purge alone. Unchanged text writes nothing.
- **Paths follow the records.** A team's folder sits under its project's current folder. When the team moves to another project (`blueprint.team_assign`) or a project is renamed, closed or reopened (`blueprint.project_update`), every page the hub wrote under the team's folder moves to the new project folder at once: the files are renamed (their history stays), links into the old folder are rewritten, `mirror_files` follows, and old folders are removed once they are empty. Files the hub did not write stay where they are, and so does their folder. A new project that takes a name already in use is picked up by the next sweep. Each move is audited as `vault.mirror_move`. The folder README lists the current paths.
- **Best effort.** A failed write (lockdown, a frozen vault, three conflicts in a row) is logged and retried by the next sweep; it never fails or slows the action that caused it.
- **Edits are replaced.** Each page starts with "Written by the Conclave hub from its records, updated <date>. Edits here are replaced." and a link to the console. An edit made in Obsidian is replaced at the next write; the file history keeps it until a reset of the vault part.
- **The page filter.** Agent text is L2. Every page drops the user part of https URLs, turns Conclave key shapes, third-party tokens (`ghp_`, `github_pat_`, `glpat-`, `xox…-`, `sk-`, `AKIA…`) and private key blocks into `[redacted]`, and leaves out body fields named like a key, token, secret, password or TOTP. The leak guard then checks each section as written: an issued key, even split across lines, withholds the section ("A section was withheld because it looked like a key") and raises `key_in_result`. No page holds a restore prompt or a pickup id.
- **Handout bodies** are cleared once their page holds them, at most 7 days later ([checkout](checkout.md) §3).
- **Who can see it.** Only the hub writes the folder. The folder name is matched without regard to case (`99 conclave` is the same folder on Windows and macOS). For an agent key every `fs.*` write under it is refused, whatever its rules say, with "99 Conclave is written by the hub; write your documents in your project folder." Reads need an allow rule whose path names the folder (`path:/<alias>/99 Conclave/**`, segment 2 with no `*`); `/<alias>/**` does not count, while the app key cap may stay a wildcard ([authorization](authorization.md)). The root listing still shows the folder's name. `file_search`, backlinks and the knowledge graph skip it. Console members see it only when it is granted to them by name (it is a restricted folder; the hub re-adds the row at boot if it is missing). The operator sees everything.
- **One writer per file.** A team's decision log (`decision_log_path`) cannot be under `99 Conclave/`.
- **Setting.** **Settings → Vault → Hub folder** turns writing on or off (default on, `GET`/`PUT /api/settings/vault`). Off stops writing and leaves the files; the protection and the purge wait stay.
- **A checkout that ended earlier.** `node scripts/mirror-import-checkout.mjs --hub <url> [--env <file>] <checkout.json>` (in `server/`) sends a saved `GET /api/checkouts/:id` to `POST /api/vault/mirror/import`, and the hub writes the same pages from it. A page that already holds a handout is never overwritten by a cleared body. The import refuses (409) a checkout whose handouts still hold their text in the hub, since the hub writes those pages itself, and a time that is not a date (400).

## Links in notes

Every place on the hub that opens a vault note from a link uses **one resolver** ([links.ts](../server/src/vault/links.ts)), with Obsidian's rules. That covers:

- the vault viewer, for the operator and for a console member (`#vault/…` and `#m/file/…`);
- links in agent text (Blueprint bodies, tasks, decisions, reports, messages);
- a Blueprint item's **Sources** and **From** line;
- the **Meetings** view.

[md.js](../server/public/md.js) reads each link's target as written. `POST /api/vault/links` (its `links` list) resolves it against what the viewer may see.

**How to write a link, in plain words.** A link names a note in one of three ways, and all three work everywhere. Like Obsidian, the hub looks next to the note first and at the top of the vault second.

1. **A path with folders**, such as `[Draft](01 Writing/Paper A/README.md)` or `[[01 Writing/Paper A/README]]`. The hub first looks for it inside the folder that holds the note: from `Papers/README.md` that is `Papers/01 Writing/Paper A/README.md`. If nothing is there, it looks from the top of the vault: `01 Writing/Paper A/README.md`. To mean only the top of the vault, start with a slash: `[Plan](/Projects/X/Plan.md)`. That form works from any note, in any folder, so it is the safest one for a home page such as `Home.md`.
2. **A path from the note's own folder only.** Start with `./` (this folder) or `../` (one folder up), as in `[Plan](../Plan.md)`. This form works only inside a note, because text outside the vault has no folder to start from.
3. **The note's name** (Obsidian's "shortest path when possible"). Write just the name or the end of its path: `[[Plan]]`, `[[X/Plan]]`. When several notes share that name, the console lists the ones you may open, nearest to the note first.

| Link | Resolves to |
|---|---|
| `[label](/Projects/plan.md)`, `[label](/<alias>/Projects/plan.md)`, `[[/Projects/plan]]` | The path from the vault root, and nothing else. |
| `[label](./plan.md)`, `[label](../Plan.md)` | The path from the folder that holds the note, and nothing else. A link that climbs above the vault root, or one outside a note, resolves to nothing. |
| `[label](Projects/plan.md)`, `[[Projects/plan]]`, `[[Plan]]`, `[[Plan\|label]]` | The first of these that finds a file the viewer may open: (1) the path from the note's folder; (2) the path from the vault root; (3) any file named `Plan` or `Plan.md`, or whose path ends with `Projects/plan.md`, case ignored. One match opens it. Several matches open a list of those visible matches only, nearest to the note first. |
| `[label](#Results)`, `[[#Results]]` | A heading in the same note. |
| `[label](https://…)` | A web page, in a new tab. Every other scheme (`javascript:`, `data:`, `mailto:` …) shows its label only. |

- **Folders.** In the vault viewer, a link to a folder opens that folder, as `[Paper A](01%20Writing/Paper%20A)` does in a papers index (a folder path has no `.md`, so write its spaces as `%20` or put it in `<…>`). A note with the same name comes first: `[[Twin]]` opens `Twin.md`, not the folder `Twin`. The folder is found the same way, next to the note first and then from the top. A member sees it only when their grant shows it, and a hidden folder gets the same answer as a missing one. An embed, a Blueprint source and the From line take files only.
- **Spaces.** A name with spaces works as Obsidian writes it: `[label](My%20Note.md)`, `[label](<My Note.md>)` and `[[My Note]]`. A hand-written `[label](My Note.md)` works too, as long as the path ends in `.md`. Other text in brackets, such as "[a](n = 12)", stays text.
- **Headings in the label.** Without a label, `[[Plan#Risks]]` reads "Plan > Risks", as in Obsidian.
- **Blueprint Sources and the From line** follow the same order. The team's granted folders are extra starting points after the note's folder. A source resolves only when it has exactly one match. An agent sometimes cites a path from its own checkout, such as `Develop/projects/…/ledger.md`: it still finds the file by its name when that name is unique.
- **Anchors are kept.** `#Heading` after any vault target opens the note at that heading. The heading is matched by its text with case and punctuation ignored, so `#Next steps` and `#next-steps` both work. A block reference (`#^id`) opens the note.
- **The extension is optional.** A path without an extension also matches the same path with `.md`, as in Obsidian.
- **Unavailable is one answer.** Some targets don't exist, some are hidden (an application folder, a restricted folder, a folder outside the member's grant), and some are refused by the path rules. All of them show as the label in an unavailable style, with the tooltip "Not available". The answer is the same whether a hidden file exists or not, and a hidden file never appears in a list of matches, so a link never tells a member that a hidden file is there.
- **Real destinations.** A resolved link has a real `href`, so it can be opened in a new tab or copied: `#vault/…` for the operator, `#m/file/<path>#<anchor>` for a member. Agent text outside the vault (Blueprint bodies, task text, decisions, reports, messages) resolves vault-root paths and wiki links the same way. A relative link there has no note to start from, so it shows as unavailable.
- **The console's own file links too.** Wherever the console names a vault file by its path (files a task's agent used or wrote, activity and audit rows, knowledge flags, grant targets, feedback links), the link has the same real address. A plain click opens the file in place, and a modified click opens a new tab.
- **Embeds.** `![[x.png]]` and `![label](x.mp3)` resolve the way the matching link does. The embed shows as a chip with the file's name. A single visible match carries the file's path for the media player, which checks access again when it loads the file. Anything else (missing, hidden, refused, or a name with several matches) shows as an unavailable chip, the same for a hidden file as for a missing one. An embed of a web or other-scheme URL stays a chip with its label.
- **Bounds.** One request checks at most 200 links (and, from an older console page, 200 paths and 200 names). A name search reads at most 20,000 visible files, like the folder tree. Links beyond these bounds show as unavailable.

## Media and attachments

The console reads a file's original bytes through one route for the operator and for members: `GET /api/vault/media?path=<virtual path>[&rev=<revision>][&as=attachment]` ([vaultApi.ts](../server/src/admin/vaultApi.ts), [media.ts](../server/src/vault/media.ts)). Text previews stay on `GET /api/vault/preview` under the preview permission. There is no other byte path in the console, and no video in this release.

- **Every request is authorized on its own.** This covers a full read, each byte range a player asks for when it seeks or resumes, and `HEAD` (metadata). The path is normalised and resolved with the vault's containment checks (no `..`, symlink escape, hidden folder or case alias). A member then needs the file itself to be visible under their grant, with restricted-folder rules applied. Being able to list a folder does not grant its files. A member's grants are read again on every request, so a grant revoked between two ranges denies the next range (`404` for a file now outside the grant, `403 export_denied` for one that lost its export permission). The refusal carries no length, range or content.
- **Originals need the export permission.** Inline playback hands the original bytes to the browser, so it counts as an export. A member needs `may_export` on a grant that opens the file: the grant whose folder holds it, or, inside a restricted folder, the grant that names that folder. This applies to inline playback and to attachments alike. The operator always may. Without the permission the console shows "Playing or downloading the original needs export permission on this folder." beside the player, and the note stays readable.
- **Bound to one revision.** The route opens the file once, records it with the vault store (which notices an external change), and checks that the open file still matches the recorded size and modification time. Otherwise it answers `409 conflict` ("The file changed while it was being read. Try again."). The revision is the `ETag`. A request with `rev` for an older revision gets `409` with `reason: changed` before any byte, so a seek can never join two versions. `If-Range` with another revision gets the whole current file (`200`). `If-None-Match` with the current revision gets `304`, after the same checks.
- **Inline only for checked types.** The type comes from the first bytes, not the name. Inline types are PNG, JPEG, GIF and WebP images, and MP3, WAV, Ogg (Vorbis or Opus), FLAC and M4A (AAC) audio. Everything else is served only as an attachment (`Content-Disposition: attachment`, `application/octet-stream`): SVG, HTML, PDF, video and anything not recognized, including an active file renamed to look like an image. `as=attachment` downloads a recognized type too.
- **Ranges.** One range per request: `bytes=a-b`, `bytes=a-` or `bytes=-n`. A range answers `206` with `Content-Range` and is capped at 8 MiB. A longer range, or an open-ended one, ends at the cap, and the player asks for the rest. A start past the end answers `416` with `Content-Range: bytes */<size>`. A request with no range, a malformed one or several ranges gets the whole file (`200`). Files over 64 MiB, which the vault does not track, are refused (`413 too_large`).
- **Headers.** Every answer carries `Cache-Control: private, no-cache` (a browser may keep a copy but must check with the hub before reusing it, and no shared cache stores it), `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `Content-Security-Policy: sandbox; default-src 'none'`, `Accept-Ranges: bytes`, the checked `Content-Type`, `Content-Length` and a `Content-Disposition` with the file's name.
- **Audit, as for previews and exports ([multi-user](multi-user.md#3-audit)).** When an external user plays a file inline, the hub records `vault.preview`. When a member downloads an attachment, the hub records `export.read` (`what: vault_file`). Any request that sends bytes counts, whatever range it starts from; `HEAD`, `304` and `416` send none and record nothing. Seeking and resuming do not flood the log: the hub records at most one row per member, file revision and representation (inline or attachment) every 10 minutes, and the row gives the file's size. A member who is not external can play an original inline without an audit row, as with text previews; the folder's export permission is still needed. The operator's reads and refused requests record nothing.
- **In the console.** The player (an image, or audio with the browser's controls) is the same in the operator's file view, the member's file page and note embeds (`![[clip.mp3]]`, `![](photo.png)` resolved to a visible file). A file row shows an image or audio icon for a type it can play. When a clip cannot play (no export permission, an unsupported type, a changed or missing file), the console shows the reason, and a **Download** button where an attachment is allowed. The rest of the note renders as usual.

## Shared folders

The admin can share vault folders with a person without a project ([folder grants](multi-user.md#12a-folder-grants)): Read by default, or Contribute. A person with Contribute creates a note (**New note** in a folder) and edits one (**Edit** on its preview) in the same vault editor as the operator ([People writing in the vault](#people-writing-in-the-vault)). The save goes through `PUT /api/vault/files` with the revision the person read, so the vault's revision history, conflict check and write lock apply as they do to an agent's `file_update`. Restricted folders inside a shared folder stay hidden and unwritable.

A person's agent works in a shared folder only as far as the person delegates it, and never beyond the grant: a Read grant caps the agent at Read ([owner enforcement](authorization.md#owner-enforcement)). The admin can give such an agent a key of its own with no team, by hand or by approving a [vault agent request](onboarding.md#a-vault-agent): a **teamless vault agent** reads and revises notes with `file_read` and `file_update` and a base revision, and has no task board, team room or Blueprint.

## People writing in the vault

The operator, and later a collaborator with **Contribute** on a folder, add, edit, rename, remove and restore files in the console. They use the same store functions as agents, so every change is a revision with a base, and a removal is a tombstone.

- **Actions.** **New note** creates a Markdown file (`.md` is added when the name has none) and opens it in the editor. **Upload** adds a file of up to 2 MB; a taken name is refused and nothing is overwritten. **Edit** opens `.md` and `.txt` files of up to 2 MB in a plain-text editor with a preview. **Rename or move** edits the path. **Remove** is always a soft delete, restorable from History. **History → Restore** brings back an earlier revision or a removed file. Folders are not renamed, moved or removed here, and links are not rewritten: the rename dialog says how many notes the viewer can read link to the file.
- **Bases.** Every update, rename, remove and restore sends the revision it read. If the file changed since, nothing is written and **no conflict is recorded**: the editor shows "Changed since you opened it" with the change, and offers **Reload**, **Copy my text** or **Keep mine**. Keep mine saves over the newer version with the base it just read, so a third change shows the banner again; the other version stays in History. Save sends the text as it was when pressed: anything typed while the save is in flight stays as unsaved changes and the editor stays open, so the next Save writes it on the revision that came back; pressing Save again during the request sends it once the first lands. A change made on disk by another program while the save commits is still recorded as an `external_during_commit` conflict ([filesystem consistency](filesystem-consistency.md)).
- **Author.** A console write records the person: author kind `operator` or `collaborator` and the user id, on the revision and on its write intent, so a write recovered after a crash keeps its author. Agents' `file_history` shows the kind and a label ("Operator", or the collaborator's display name), never a console user id.
- **Refused paths.** Every action refuses, at both ends of a rename: `99 Conclave/` in any letter case (nobody writes there; the hub replaces its pages), hidden names (`.obsidian`, `.trash`, `.git`, `shares`, `.hub-tmp` and the vault's other hidden names), a case alias of an existing file, a name ending in a dot or space, and Windows-reserved names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, with or without an extension). The console does not offer the actions there and says why.
- **Members.** Until the operator decides the scope of Contribute, a member may only create a note and edit text, in folders where their folder grant gives Contribute (`MemberScope.canWrite`); uploads, rename, remove and restore answer members `403 admin_only`. A member edits in the member console's editor, which saves through the same routes. Rights are checked again at save; a member who can read the folder but not contribute gets `403 read_only` ("This folder is read only for you."), and a file the member cannot read answers `404`, as if it did not exist.
- **Reading text to edit.** The editor reads the file through the media path above with `as=text`: a `.md` or `.txt` file of up to 2 MB, served whole as `text/plain`, with its revision as the ETag. It is allowed for the operator, and for a member only with Contribute on the file's folder; an external member's read is audited like a preview.
- **Pause and lockdown.** The write pause (`emergency.writes_disabled`) or the vault's lockdown refuses every console write with `423 lockdown` and its reason.
- **Audit.** Every write records `vault.file.create`, `vault.file.update`, `vault.file.rename`, `vault.file.delete` or `vault.file.restore` with the path, the revision and the author kind, and shows in the file's Activity. An agent's writes are recorded the same way (actor: the agent), and a refused agent write is `vault.file.refused` with the code and reason ([filesystem consistency](filesystem-consistency.md#outcomes-and-conflict-records)).
- **Routes.** `POST /api/vault/files` (a note as JSON `{ path, text }`, or an upload as `application/octet-stream` with `?path=`), `PUT /api/vault/files` (`{ path, text, base_revision }`), `POST /api/vault/files/rename` (`{ from, to, base_revision }`), `DELETE /api/vault/files?path=…&base_revision=…` and `POST /api/vault/files/restore` (`{ path, revision, base_revision, to? }`, where a removed file's base is `absent`). Each is CSRF-protected. `GET /api/vault/backlinks?path=…` counts the notes the viewer can read that link to a file.

## In the console

**Vault → Knowledge** shows operator health (coverage by folder, claims, communities, open flags, queued and parked jobs, spend against the daily cap, verification and curator throughput), searches entities, lists flags with **Mark fixed** and **Dismiss**, lists jobs by state, and runs **Refresh** (recompute communities). **Settings** edits token budgets (used against cap), model-tier patterns and priority folders, picked from the vault tree and stored vault-relative (`Cases/`). It uses the [admin API](../server/src/admin/graphApi.ts); what the view must answer is in [Dashboard UX](dashboard-ux.md#knowledge).

## Organizing project files

Blueprint items cite vault files as their sources, and the console resolves each one per viewer (docs/blueprint.md §2.7). A stable project folder helps keep citations valid. The following layout is a convention for operators.

- One folder per project, `Projects/<KEY>/`, with `Notes/`, `Records/` (ledgers, registers, experiment logs), `Papers/` and `Reviews/`.
- Keep one working copy and use separate backups for recovery.
- Each team's grants point at its project folder, so source lookup finds the files.
